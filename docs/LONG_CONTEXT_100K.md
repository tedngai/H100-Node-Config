# 100K c1 cold retrieval baseline

**Historical protocol/results.** New benchmark acceptance follows
[BENCHMARK_POLICY.md](BENCHMARK_POLICY.md); old zero-queue requirements below
do not govern new capacity-first runs. Original results remain unchanged.

**Status:** one attempt was blocked at preflight by unrelated traffic; the later
explicitly approved attempt completed successfully on 2026-10-14. This is one
bounded long-context retrieval check after completion of the 32K baseline screen.
It does not authorize a larger matrix, throughput qualification, candidate
configuration, or server change. Any repeat needs separate approval.

## Proposed scope

- Preserved `baseline` profile only; DP1 and unchanged effective configuration.
- One client at a time (**c1**), **100,000 input tokens**, up to **1,024 output
  tokens**, retrieval mode, cold namespace, and **three serial rounds**.
- Maximum of **three inference requests**. No warmup, concurrent clients, retries,
  decode-throughput run, cache flush, or automatic progression to 200K/near-limit.
- Prompts are generated by the existing CPU-only tokenizer using unique per-round
  session namespaces. The run records prompt hashes and actual cache-hit counts;
  `cold` does not guarantee zero hits, and no cache flush is implied.
- The existing synthetic retrieval task places one code near the beginning, middle
  and end of the prompt. Each response must recover all three codes. Output is
  normally terminated (not forced); 1,024 is the maximum output length.
- Fresh token-budget guard: `1 × (100,000 + 1,024) = 101,024` token slots, about
  **6.36%** of the recorded 1,587,968-token shared pool. This guard is not a promise
  against hybrid-state exhaustion or OOM.

## Measurement and stop rules

Use the existing **strict** `tests/benchmark.py` retrieval path, report kind
`benchmark`; do not use or extend the fixed 32K scheduling-aware script. The normal
zero-queue rule remains in force: any sampled waiting request fails the run and
prevents later rounds. Do not reinterpret waiting as benign prefill behavior. A
separate diagnosis would need its own reviewed protocol and approval.

Before execution, require explicit approval for this workload and a coordinated
quiet window. Capture a fresh read-only inventory; verify the baseline profile,
container/image/argv/start identity, healthy GPU query, current cached-model metadata,
and idle `/v1/loads`. Check the recent generation-access log and compare the current
identity/configuration with the latest post-reboot evidence, not only the older
pre-reboot snapshot. Confirm there is no unrelated inference traffic. Run the
offline setup validation; it sends no inference.

Both `--execute` and `--confirm-idle` are required. The harness checks DP1, readiness,
disabled auto-truncation, input/context limits, exact 100,000-token accounting,
retrieval recall, retractions, and configuration health. Monitor read-only scheduler
telemetry without enabling metrics. Stop the run on any request/retrieval failure,
token mismatch/truncation, sampled queueing, retraction, stale/missing/conflicting
telemetry, unexpected active-count/traffic evidence, server/configuration drift,
health failure, or inability to establish idle after the invocation. Do not submit
another round or retry after a failure; preserve the partial report and audit.
Requests already submitted may remain in flight; no implicit cancellation is
available.

After the invocation, audit access records: exactly three successful `/generate`
requests must match the report, with no unrelated generation/chat requests. Confirm
the server is idle and configuration/identity is unchanged before considering any
separate next step. If any check fails, retain the failed evidence and stop.

## Interpretation

This is a functional long-context/retrieval screen at c1, **not** a throughput or
production qualification. Three requests are insufficient for p95 or reliable-tail
claims. A pass means all retrieval and harness checks passed for these synthetic
prompts; it does not establish recall for real workloads, fairness, memory safety
under load, or viability at higher concurrency. The older strict c2 32K queue failure
remains failed and is not changed by this c1 check.

## Recorded result

The 18:26 UTC run passed all three serial retrieval rounds. Each prompt was exactly
100,000 tokens; all three expected codes were recovered in every response. Every
request reported zero cached tokens, 40 completion tokens, and zero retractions.
Sampled peak waiting was zero (peak running was one). Median TTFT was **3.377 s**;
median end-to-end latency was **3.468 s**. The reported **11.53 output tok/s** is
only the short 40-token retrieval answer rate, not decode-throughput qualification.
p95 is unavailable with three requests.

The post-run audit matched exactly three successful `/generate` requests and found
the service idle with no other inference routes. See the benchmark report and
post-traffic checkpoint linked in `docs/results.md`. This remains a synthetic c1
retrieval screen, not real-workload recall, production qualification, or approval
for 200K, higher concurrency, or candidates.
